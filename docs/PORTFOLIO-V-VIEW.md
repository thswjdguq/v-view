## 1. 프로젝트 요약 — 공개용 초안

### 한 줄 소개

**v-view는 지원 정보에 맞춘 AI 질문, 카메라 기반 응시 지표, 피드백 리포트를 연결한 Flutter 면접 연습 앱입니다.**

### 프로젝트 소개

혼자 면접을 연습할 때는 자신의 경험에 맞는 질문을 준비하고 연습 결과를 돌아볼 자료를 남기기 어렵습니다. v-view는 직종·회사·자기소개서를 입력하면 맞춤 질문을 생성하고, 답변에 따라 꼬리질문을 이어갑니다. 면접 중에는 얼굴 방향을 바탕으로 응시 상태를 추정하고, 종료 후 답변과 응시 지표를 활용한 피드백 및 연습 기록을 제공합니다.

이 프로젝트에서는 화면 구현, 여러 화면에 걸친 상태 관리, 외부 AI API 연동, 카메라 프레임 처리, 로컬 기록 저장을 하나의 사용 흐름으로 연결했습니다.

## 3. 설계와 기술 선택 — 공개용 초안

### 화면과 상태·외부 연동의 책임 분리

프로젝트를 UI, State, Domain, Data로 나누어 화면 표현, 상태 전환, 데이터 모델, 외부 연동의 책임을 구분했습니다. 면접 진행 상태는 Riverpod의 StateNotifier로 관리하고, AI 요청과 로컬 저장은 별도 서비스·데이터 소스로 구성했습니다.

```text
UI: 입력과 결과 표시
  ↓ Provider 조회·호출
State: 세션 진행과 상태 변경 조율
  ↓ 서비스·데이터 소스 호출
Data: AI API·ML Kit·Hive·Firebase 연동

Domain: 각 부분이 사용하는 질문·세션·리포트 모델
```

이 도식은 책임 구분을 요약한 것으로, 실제 모든 import가 엄격한 단방향 규칙을 만족한다는 주장으로 사용하지 않는다.

| 선택 | 이 프로젝트에서 설명할 이유 | 근거 |
|---|---|---|
| Riverpod | 질문·답변·타이머 등 공유 상태를 화면과 분리하고, 테스트에서 의존성을 대체하기 위해 사용 | `docs/ADR/ADR-002-state-management.md`, `v_view/test/state/interview/interview_notifier_test.dart` |
| Hive | 리포트와 기록 요약을 Map 기반으로 직렬화해 기기에 저장 | `docs/ADR/ADR-003-local-storage.md`, `v_view/lib/data/local/` |
| ML Kit Face Detection | 카메라 프레임에서 얼굴 방향 정보를 얻어 기기 내에서 응시 상태를 추정 | `v_view/lib/data/remote/gaze/gaze_analyzer.dart` |
| Dio·OpenAI API | 입력 정보와 답변을 전달하고 JSON 형식의 질문·피드백 응답을 모델로 변환 | `v_view/lib/data/remote/ai/claude_api_service.dart` |

기술 이름 옆에는 숙련도 퍼센트 대신 실제 구현한 동작과 선택 이유를 적는다. 의존성 버전을 넣을 때는 선언 범위와 실제 설치 버전을 구분한다.

## 4. 문제 해결 사례 1 — 이전 면접 데이터 잔류

### 공개용 초안

**문제:** 새로운 면접을 시작했는데 이전 세션의 입력과 질문이 남는 문제가 있었습니다.

**원인:** 화면 이동만으로는 전역 Provider의 상태가 초기화되지 않았고, 기존 질문을 재사용하는 조건도 남아 있었습니다.

**해결:** 새 면접 진입 시 입력·면접·시선 상태를 초기화하고, 질문 화면에서도 첫 화면 구성 전에 기존 질문을 비웠습니다. 이후 질문 생성을 시작하도록 순서를 나누었습니다.

**코드에서 확인한 변경:** 홈과 설정 진입점에서 reset을 호출하며, 질문 화면은 initState에서 reset 후 첫 프레임 뒤 start를 호출합니다. 질문이 아직 없는 초기 상태는 로딩 화면으로 처리합니다.

**배운 점:** 전역 상태의 수명은 화면의 수명과 다르며, 새 작업의 시작 조건과 상태 초기화 시점을 명시해야 한다는 점을 배웠습니다.

### 근거

- `v_view/lib/ui/home/home_screen.dart`: `_startNewSession()`
- `v_view/lib/ui/session_setup/session_setup_screen.dart`: `initState()`
- `v_view/lib/ui/questions/question_list_screen.dart`: `initState()`, `_Body.build()`
- `WIKI.md`: TS-002, TS-003
- Git 커밋: `6c3cacd`, `6787077`

### 추가할 증거

- 기존 세션 A → 새 세션 B에서 입력과 질문이 섞이는 개선 전 장면
- 동일한 순서로 재현했을 때 초기화되는 개선 후 장면
- 해당 코드의 핵심 부분과 커밋 링크

실기기 재현 확인 전에는 ‘재발 0건’, ‘완전히 해결’, 성공률 같은 수치를 붙이지 않는다.

## 5. 문제 해결 사례 2 — 꼬리질문 생성 제어

### 공개용 초안

**문제:** 답변마다 추가 질문을 생성하면 면접 흐름이 길어지고, 꼬리질문이 반복될 수 있었습니다.

**해결:** 초기에는 최대 2단계로 제한했지만, 답변 내용에 따라 필요한 확인만 진행하도록 변경했습니다. 이전 문답과 현재 답변으로 `needsFollowUp`·질문 종류·필요한 이유·실제 답변 인용을 받습니다. 앱은 인용의 존재를 검증하고 같은 질문을 차단하며, 사용자는 기본 질문으로 넘어갈 수 있습니다. AI 응답이 실패하거나 근거가 유효하지 않으면 안내 후 기본 질문 진행을 계속합니다.

**배운 점:** 질문 횟수와 실제 필요성은 다른 문제입니다. AI 판단과 별개로 근거·반복·중복 제출·실패 복구를 앱에서 검증하고, PC 프로세스의 요청 한도로 사용량을 제어합니다. 작은 가상 시나리오 확인을 모델 정확도 성과로 표현하지 않습니다.

### 근거

- `v_view/lib/data/remote/ai/claude_api_service.dart`: `_buildFollowUpPrompt()`, `_parseFollowUp()`
- `v_view/lib/state/interview/interview_provider.dart`: `nextQuestion()`, `nextBaseQuestion()`, `_sameQuestion()`
- `v_view/test/state/interview/interview_notifier_test.dart`: Fake API를 활용한 질문·답변·꼬리질문 삽입 테스트 코드
- `WIKI.md`: TS-004

### 추가할 증거

- 기본 질문 → 1차 → 2차 꼬리질문 → 다음 기본 질문의 진행 예시
- 추가 질문 불필요 응답 및 요청 실패 시 진행 예시
- 깊이 제한 자체의 검증 결과. 현재 테스트가 모든 경계를 검증한다고 단정하지 않는다.

## 6. 핵심 구현 사례 — 카메라 입력을 지표로 변환

### 공개용 초안

카메라 프레임을 ML Kit 입력 형식으로 변환하고, 얼굴의 좌우 회전·기울기 각도를 기준으로 응시 여부를 추정했습니다. 응시율은 전체 측정 프레임 중 응시 프레임의 비율로 계산하고, 연속 1초 이상 분산된 구간만 분산 횟수로 집계하도록 구성했습니다. 얼굴 검출 비율에 따라 측정 품질도 구분합니다.

시선 분석은 **얼굴 방향 기반의 추정**입니다. 정밀한 눈동자 추적이나 면접 역량의 정확도 검증을 수행한 것으로 표현하지 않습니다.

### 근거

- `v_view/lib/data/remote/gaze/camera_frame_converter.dart`
- `v_view/lib/data/remote/gaze/gaze_analyzer.dart`: `_isLookingAtCamera()`, `computeMetrics()`
- `v_view/lib/state/gaze/gaze_provider.dart`: 프레임 처리와 지표 상태 관리
- `v_view/test/data/remote/gaze/gaze_analyzer_test.dart`: 응시율, 1초 경계, 미검출, 품질 분류 테스트 코드

### 제시할 자료

- 카메라 입력 → 변환 → 얼굴 방향 추정 → 프레임 집계 → 리포트 구조도
- 1초 미만·정확히 1초·1초 초과 분산을 검증한 테스트 실행 결과
- 실제 기기·조명·카메라 조건을 기재한 시연

## 7. AI 활용과 본인 기여 — 작성 시 확인

문서에는 Manifest AI로 기획 초안, Google Stitch로 디자인 시안, Claude Code로 구현·문서 초안을 생성하고 개발자가 검토하는 과정이 기록되어 있습니다.

공개 원고에는 아래 형식으로 **본인이 실제로 한 판단**을 추가합니다.

> [도구]가 제안한 [구현 또는 시안]에서 [문제]를 발견했습니다. [재현·검토 방법]으로 원인을 확인하고 [수정 방향]을 결정했습니다. [코드·화면·테스트]로 결과를 확인했습니다.

후보 사례:

- 이전 질문 잔류 문제를 재현하고 세션 초기화 시점을 정한 과정
- AI가 생성한 버튼 구현의 border assertion 문제를 찾아 수정한 과정
- 꼬리질문 깊이 제한과 실패 시 진행 규칙을 정한 과정

근거: `AUTHORING.손정효.md`, `WIKI.md`, 관련 커밋. 이번 후속 변경은 AI 코딩 에이전트의 구현·테스트를 포함하며 본인의 검토·의사결정 범위는 직접 확인해 서술한다.

전체 코드와 설계를 수작업으로 작성했다는 표현이나 AI가 만든 변경을 본인이 검증한 사실 없이 직접 해결했다고 단정하는 표현은 사용하지 않습니다. 프로젝트 구현 사실과 개인 기여는 구분합니다.

| 리포트 fallback | 실제 generate 호출로 측정 불가 안내 및 저장 성공·실패 경로 검증 | AI 서비스의 실제 응답 품질 별도 검증 |
| UI | 신규·저장 리포트 통합, 답변 보존·시간 재개·재시도·작은 화면 위젯 테스트. Android 샘플 리포트 시각 확인 | 실제 사용자 흐름 전체 시연과 기기별 확인 |

| 성능·사용성 | 이번 정리에서 측정하지 않음 | 응답 시간·사용 과제 성공 여부 등을 측정한 경우만 수치로 사용 |
| 플랫폼 | Android/iOS 등의 프로젝트 파일 존재 | 실제 검증한 기기와 기능만 지원 범위로 표기 |

주의할 기존 문서·구현 차이:

- 기존 ‘답변 안정감·표현력·총점’은 제거하고 실제 답변 완료율·답변 시간·응시 지표를 표시하도록 개선했습니다. 완료율은 답변의 질을 평가하는 점수와 구분합니다.
- 시선 분석은 얼굴 방향 추정이며 정확도 수치를 측정하지 않았습니다.
- 로컬 입력 저장 코드와 Firebase 사용자 프로필 저장, 외부 AI 요청이 존재합니다. ‘모든 데이터는 기기에만 남는다’는 문구를 사용하지 않습니다.
- 앱의 `.env` 로딩·자산 포함·OpenAI 직접 키 헤더를 제거하고 Firebase 인증 중계로 변경했습니다. 키는 서버에서만 사용합니다. 서버 배포·실제 인증 연결 검증을 마쳤다는 뜻으로 사용하지 않습니다.
- 서버 제한은 프로세스 단위이며 공개 다중 사용자 서비스 전에는 공유 한도·비용 관리·모니터링이 필요합니다.
- 일부 ADR의 ‘공식 패키지’, 모든 레이어의 의존 규칙 충족 등 넓은 주장은 별도 확인 없이 복사하지 않습니다.

## 13. 후속 문제 해결 사례 — 데모 의존성 연결

**문제:** 샘플 리포트와 개별 상태 테스트는 통과했지만, Android에서 데모 질문 시작 버튼을 누르면 실제 AI 서버 주소가 없다는 오류가 나타났습니다.

**원인:** 중첩된 ProviderScope에서 API만 대체하고 면접 상태 Provider는 부모 컨테이너에서 생성되어 실제 서비스를 참조했습니다. 테스트가 샘플 API를 직접 호출하는 경로에 치우쳐 있어 화면 진입 경로의 연결 문제를 놓쳤습니다.

**수정:** 데모 입력·면접 상태를 데모 Scope에 명시적으로 연결하고 불필요한 부모 Scope를 제거했습니다. 데모 입력 상태는 메모리에서 관리하며, 완료한 답변·기록은 별도 Hive 저장소에 실제로 저장합니다.

**검증:** 부모 Scope가 존재하는 화면 이동을 회귀 테스트로 추가해 실패를 재현하고 수정 후 통과를 확인했습니다. 이어 Android 데모에서 질문 진입·답변·리포트 저장과 앱 재실행 후 기록 재열람을 확인했습니다. 이는 실제 마이크·외부 AI 호출 검증과 구분합니다.

근거: `v_view/lib/demo/demo_app.dart`, `v_view/lib/main_demo.dart`, `v_view/test/demo/demo_flow_test.dart`, `docs/verification/`.
이 사례는 AI 코딩 에이전트가 수행한 후속 개발·검증을 포함합니다. 본인의 검토·재현·의사결정 범위는 직접 확인해 서술합니다.

## 14. 후속 문제 해결 사례 — 삭제 완료와 데이터의 수명

**문제:** 기록을 삭제하면 목록에서 사라졌지만 상세 답변은 다른 Hive box에 남아 있었습니다. 저장소 작업의 Future도 기다리지 않아 디스크 쓰기 실패를 화면에서 알 수 없었습니다.

**수정:** 상세·요약 삭제를 하나의 삭제 작업으로 묶고 두 작업을 모두 기다린 후 목록을 갱신했습니다. 전체 삭제는 시작 시점의 ID 목록으로 범위를 고정해 이후 생성된 기록을 함께 지우지 않도록 했습니다. 삭제 중 중복 조작을 막고 오류가 발생하면 재시도할 수 있게 했습니다.

**검증:** 실제 임시 Hive 저장소에서 개별·전체 삭제, 고아 상세 정리, 저장 완료 대기, 부분 실패와 재시도, 동시 저장, 저장소 재개방을 테스트했습니다. 작은 화면·큰 글자에서 삭제 대화상자 조작도 확인했습니다.

**한계와 판단:** 서로 다른 box는 원자적으로 삭제되지 않습니다. 중간 실패 시 상세부터 정리한 뒤 재시도로 남은 요약을 삭제하는 방식을 선택했습니다. 앱 강제 종료까지 포함하는 자동 복구 저널은 후속 검토 과제입니다.

근거: `v_view/lib/data/local/record_deletion_datasource.dart`, `v_view/lib/state/history/history_provider.dart`, `v_view/test/state/history/record_deletion_test.dart`.

## 15. 후속 문제 해결 사례 — AI 생성과 저장 재시도의 책임 분리

**문제:** AI 피드백을 받은 뒤 디스크 저장이 실패하면 결과 화면이 오류 화면으로 바뀌었습니다. ‘다시 시도’는 리포트 생성 전체를 실행해 AI를 다시 요청하고 새 ID를 만들었습니다. 상세 리포트 저장만 성공한 경우에는 이전 상세가 고아 기록으로 남을 수 있었습니다.

**재현:** 화면 테스트에서 첫 저장만 실패하도록 주입한 후 재시도를 눌렀습니다. 기대한 AI 호출 1회와 달리 2회가 발생했고, 실패 화면에서는 리포트 복사 버튼도 사라지는 것을 확인했습니다. 실제 과금 호출 대신 호출 수를 기록하는 테스트 API를 사용했습니다.

**수정:** 리포트 생성과 저장을 분리하고 `generating → saving → done/error` 상태를 명시했습니다. 실패해도 생성한 답변·피드백·ID·작성 시각을 유지합니다. ‘저장 다시 시도’는 같은 ID로 상세와 요약만 덮어써 복구하며 AI에 새 요청을 보내지 않습니다. 저장 완료 전에는 성공 안내와 다음 행동 버튼 대신 저장 상태를 표시하고, 실패 중에도 질문을 펼치고 전체 내용을 복사할 수 있게 했습니다.

**검증:** 실제 임시 Hive 저장소에서 상세 실패·요약만 실패한 부분 저장·재시도·저장소 재개방을 확인했습니다. 중복 재시도, 늦은 AI/저장 완료, 종료한 상태 객체, 요청 중 입력 목록 변경도 검증했습니다. 320×740·글자 1.8배에서 오류 안내·답변 펼치기·복사를 확인했습니다. 이번 회귀 테스트는 상태 7개·화면 3개입니다.

**한계:** 두 box 쓰기는 원자적 트랜잭션이 아닙니다. 재시도 대상은 실행 중 메모리에 보관하므로 앱 강제 종료 후 자동 복구를 보장하지 않습니다. 화면에서 앱을 닫기 전에 복사하거나 저장을 재시도하도록 안내합니다. 실제 API 비용 절감액을 측정한 사례로 표현하지 않습니다.

근거: `v_view/lib/state/report/report_provider.dart`, `v_view/lib/ui/report/report_screen.dart`, `v_view/test/state/report/report_save_recovery_test.dart`, `v_view/test/ui/report/report_save_recovery_test.dart`.
이 사례도 AI 코딩 에이전트가 수행한 후속 개발을 포함합니다. 본인이 직접 이해·재현·검토한 범위에 맞춰 편집합니다.

## 16. 후속 설계 변경 — 클라우드 배포 없이 실제 GPT 연결

**요구:** 클라우드 서버를 배포할 수 없는 환경에서 개인 PC의 GPT 키로 질문 생성과 답변 평가를 실행해야 했습니다.

**선택:** 키를 앱에 넣는 대신 PC의 loopback 프로세스에서만 보관했습니다. Android는 USB 포트 연결을 통해 요청하며, 기본 앱 진입점도 Firebase 로그인 없는 개인 PC 모드로 바꿨습니다. 카메라·마이크와 실제 피드백 경로는 유지하고, 샘플 응답으로 실패를 숨기지 않습니다. 기존 제품·데모 기록과 다른 `local_ai` 저장소를 사용합니다.

**범위 제어:** PC 프로세스는 127.0.0.1에만 수신하고 외부 Host·웹 Origin·비로컬 접속을 거부합니다. 입력 크기·메시지 수·PC당 요청 횟수·동시 요청·출력 토큰 제한을 공통 처리합니다. 기존 프로젝트 키를 옮기는 준비 명령은 키 값과 다른 비밀 설정을 출력하지 않습니다.

**증거:** 자동 테스트 외에 실제 Flutter 요청 코드로 가상 지원 정보의 질문 생성 1회·꼬리질문 1회·평가 1회를 OpenAI에 요청해 응답 파싱을 확인했습니다. 질문 2개와 근거가 포함된 개선 의견 3개를 받았습니다. [가상 입력과 실제 API 응답](verification/v-view-local-ai-live-2026-11-11.json)을 확인할 수 있습니다. 클라우드 배포·Firebase 인증·실제 사용자 성과 검증과 구분합니다.

**한계:** PC가 켜져 있고 로컬 프로세스와 USB 연결이 유지돼야 합니다. 이 경로는 개인용 Android 디버그 실행이며 공개 다중 사용자 서비스의 인증·운영 경험을 의미하지 않습니다. 휴대폰 마이크 정확도와 iOS는 별도 검증이 필요합니다.

근거: `v_view/lib/local/local_ai_app.dart`, `v_view/lib/main.dart`, `server/src/local.js`, `server/src/app.js`, `docs/LOCAL-AI.md`. AI 코딩 도구의 후속 구현을 포함하므로 본인 검토·재현 범위에 맞춰 사용합니다.

## 17. 후속 UX 개선 — 지원 자료의 구조와 면접 공개 시점

**문제:** 하나의 소개 입력란으로는 지원자 배경과 서로 다른 자소서 문항을 구분하기 어려웠습니다. 시작 전에 모든 질문을 보여주면 즉석 답변을 연습하는 흐름도 약해졌습니다.

**변경:** 이름을 받지 않고 선택 나이·학력·자격증, 이력서 요약과 자소서 질문·답변 세 쌍으로 분리했습니다. 같은 모델 직렬화를 일반 자료 저장과 임시 면접 복구에 사용하고 기존 소개 형식을 읽습니다. 확인 후 시작하면 준비 화면에서 첫 질문으로 바로 이동하고 이후에는 현재 질문만 공개합니다. 홈은 둥근 카드·버튼과 자체 V-Bot을 사용해 시작 행동과 연습 순서를 강조하며, 실제 저장된 연습 횟수와 연속일만 표시합니다.

**검증:** 실제 임시 Hive 저장·재개방, 문항별 값 유지, 선택 프로필 없이 시작, 새 자료의 AI 요청 전달, 생성 실패 재시도와 다음 질문의 순차 공개를 자동 검증했습니다. 320×740·글자 1.6배에서 설정 화면의 모든 구역과 확인 버튼에 접근합니다. TEST 표시가 있는 위젯 렌더링은 실제 휴대폰 사용성 실험이나 사용자의 성과 자료가 아닙니다.

근거: `SessionInput`, `SessionInputNotifier`, `SessionInputLocalDatasource`, `structured_application_test.dart`, `structured_application_screen_test.dart`, `question_list_screen_test.dart`. 개발·테스트·화면 수정에는 AI 코딩 에이전트가 참여했습니다. 사용자는 요구사항과 방향을 제시했으며 본인이 직접 이해·검토·수정한 범위는 별도로 확정해야 합니다.

## 18. 후속 안정화 — 근거 있는 추가 확인과 재연습

횟수 제한으로 질문을 끝내던 방식에서 이전 문답을 참고해 필요한 확인·근거 질문을 판단하도록 바꿨습니다. 실제 답변 인용을 검증하고 반복 질문을 차단하며 오류 시 기본 질문으로 진행합니다. 작성 중 답변·시간 복구와 저장 기록의 평가 재시도·동일 질문 재연습으로 연습을 이어갈 수 있도록 연결했습니다.

가상 문답의 실제 GPT 확인에서는 형식 오류, 해소한 모순, 원문과 한 글자가 다른 인용 같은 실패도 관찰했습니다. 인용 검증을 완화해 통과시키지 않고 사용자에게 안내 후 기본 질문을 진행합니다. 소수 사례를 정확도나 사용자 효과 수치로 쓰지 않습니다. 결과·제약은 [검증 기록](verification/README.md)을 따릅니다.

## 19. 후속 입력 UX — 학교 검색과 여러 자격증 선택

**문제:** 학교와 자격증을 모두 직접 입력하면 오타가 생기고, 여러 자격을 하나의 긴 문자열로 관리하게 됩니다. 검색 결과의 선택과 실제 저장을 구분하지 않으면 뒤로 나가도 입력이 바뀌는 문제가 생길 수 있습니다.

**변경:** 공개 자료에서 명칭·학교 지역·종류만 추려 앱에 포함했습니다. 일부 이름·약칭·띄어쓰기로 검색하고, 자격증은 여러 개를 선택해 완료 시 칩으로 반영합니다. 개별 삭제와 목록에 없는 항목 직접 추가를 제공합니다. 학교는 선택 이름과 전공·졸업 상태를 나눴습니다. 새 자격 배열과 기존 문자열을 함께 읽어 이전 입력을 유지하며, 자료 저장·임시 복구·AI 질문 입력까지 연결했습니다.

**실패 재현과 수정:** 직접 추가 안내가 선택 완료 버튼을 가려 실제 저장이 되지 않는 화면 테스트 실패를 관찰했습니다. 안내 대신 선택 목록을 즉시 보여주고 상단·결과를 한 스크롤 안에 두어 키보드·큰 글자에서도 완료 버튼에 접근하도록 수정했습니다.

**검증과 범위:** 실제 앱 자산의 검색 결과, 여러 항목의 선택·삭제·완료·취소, 로딩 실패 중 직접 추가, 320×740·글자 1.6배·키보드 높이 260 조건을 자동 검증했습니다. 학교·여러 자격·준비 시간·카메라 옵션은 실제 임시 Hive 저장소를 닫고 재개방해 확인했습니다. 목록은 현행 자격·취득 여부·학적 사실을 검증하는 서비스가 아닙니다. 과거 자격 명칭도 포함되며 출처·기준일·갱신은 [목록 안내](../v_view/assets/catalogs/SOURCES.md)를 따릅니다.

## 20. 후속 연습 UX — 준비 시간과 답변 보존의 경계

**문제:** 질문을 읽는 동안 답변 시간이 줄고, 시간이 끝나면 인식된 답변을 확인하기 전에 자동 제출됐습니다. 준비·일시정지 전후의 시선 프레임을 이어 계산하면 실제로 측정하지 않은 대기 시간을 분산으로 합산할 수 있었습니다.

**변경:** 준비 시간을 답변 시간과 분리하고 없음·15초·30초 또는 바로 시작을 제공합니다. 시간이 끝나면 마이크의 마지막 인식 문장을 보존하고 제출·30초 연장을 사용자가 선택합니다. 빈 답변은 확인 후에만 건너뜁니다. 카메라 없이 연습할 수 있고 미측정 이유를 리포트에 유지합니다.

**시선 경계의 재현:** 정지 전후 각각 0.5초의 분산 프레임 사이에 20초 간격을 두었을 때 분산 1회가 잘못 계산되는 실패를 재현했습니다. 정지 전에 시작한 분석이 재개 후 도착해 섞이는 실패도 확인했습니다. 측정 구간 번호로 분산 계산을 닫고, 이전 구간의 늦은 결과를 버린 뒤 두 테스트와 기존 1초 임계값 테스트가 통과했습니다. 응시율에 가짜 프레임을 추가하지 않습니다.

이 구현·자동 테스트·위젯 화면 생성은 AI 코딩 에이전트의 후속 작업을 포함합니다. 개인 기여로 공개할 때는 본인이 직접 이해·검토·수정한 범위를 구분해야 합니다. 실제 휴대폰의 음성·카메라 정확도와 사용자 연습 효과를 측정한 성과로 표현하지 않습니다.
